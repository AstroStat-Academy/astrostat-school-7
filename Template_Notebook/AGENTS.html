AGENTS#

This file provides guidance to Claude Code (claude.ai/code), Codex, or other agents when working with code in this repository.

Project Overview#

Jupyter Book site for the 7th AstroStatistics School (Rome, 2026). Contains lecture notebooks for astrostatistics topics. Deployed to GitHub Pages automatically on push to main.

The course will use:

  1. Jupyter Notebooks

  2. pptx files

  3. Other formats a teacher may choose

The instructions in this file solely refer to the Jupyter Notebooks.

When instructed to produce other file types, ask the user and work interactively.

Audience & Learning Objectives#

The audience is composed by an international mixture of Master’s, PhDs, and Postdocs who work in the field of Astrophysics, Astronomy, or very closely related fields.

Remember that the main learning objectives the students shall achieve are:

  • Understand the statistical or machine learning methods presented in the lecture.

  • Apply the practical methods that convert the thory into Python coding.

  • Understand how to simply re-utilize what they have seen in the lectures in their own daily work.

Architecture#

  • _config.yml — Jupyter Book configuration (title, repo link, Colab launch buttons, MyST extensions)

  • _toc.yml — Table of contents defining chapter order; each chapter points to a notebook file

  • index.md — Landing page

  • environment.yml — Conda environment (Python 3.13, jupyter-book <2, scientific stack)

  • Topic directories named as <Topic_Name> (e.g., Gaussian_Processes/, Template_Notebook/) — contain .ipynb notebooks.

Other top-level items:

  • docs/superpowers/{specs,plans}/ — dated design specs and implementation plans for lectures (e.g. 2026-06-22-l06-design.md), produced via the brainstorming/planning skills before building a notebook.

Topic Folder Layout#

Each topic lives in its own top-level folder <Topic_Name>. The folders are self-contained: a topic reads only from its own data/ and images/ subfolders, never from another topic’s. A topic folder may contain more lectures in the form of notebooks, although it is usually only one lecture per topic.

Per-topic folder contents:

  • <Topic_Name>/<Lecture title>.ipynb — a deliverable lecture notebook. These are the only notebooks you create or edit when asked for “the lecture”.

  • <Topic_Name>/<Lecture title> inclass.ipynb — the teacher’s in-class variant of a lecture, maintained by the user. Never create, edit, or read these when authoring a lecture. These files may or may not exist.

  • <Topic_Name>/data/ — datasets the notebook loads. Often synthetic and generated by a committed script (e.g. make_dataset.py, make_dataset_outliers.py) that writes the CSV/DB the notebook reads. When a lecture needs data, prefer generating it with such a script (seeded, reproducible) over hand-editing files.

  • <Topic_Name>/images/ — illustration assets. Illustrations can simply be images stored there by the user, or generated via scripts contained in the very same folder. Each generated illustration is a fig_*.py generator script paired with its output fig_*.png (see the Figures rules below). The notebook imports the .png; the .py is never run from inside the notebook.

Separate exercise notebooks: most exercises live inline in the lecture notebook, but a lecture may also ship a standalone exercise.

Adding A New Topic#

  1. Create a directory named <Topic_Name>/ with data/ and images/ subdirectories as needed.

  2. Register the notebook path in _toc.yml under chapters:.

  3. Add static paths for data/ and images/ subdirs in _config.yml under html.static_path.

  4. Add a short description in index.md.

  5. Add any new dependencies to environment.yml.

Environment#

Notebooks run under the astrostat-7 conda env; python/jupyter are not on the base PATH. Activate it (conda activate astrostat-7) before running notebooks or data-generation scripts. The pinned stack is in requirements.txt: numpy, pandas, matplotlib, seaborn, statsmodels, scipy.

Build & Development#

# Create/activate conda environment
micromamba create -f environment.yml
micromamba activate astrostat-school

# Install Jupyter kernel (needed for notebook execution)
python -m ipykernel install --name astrostat-school --display-name "Python (astrostat-school)" --user

# Build the book locally
jupyter-book build .

# Output goes to _build/html/

Notebook execution is set to "off" in _config.yml — the build does not re-run notebooks; it uses stored outputs.

Deployment#

Pushing to main triggers .github/workflows/deploy.yml, which builds the book with micromamba and deploys _build/html/ to the gh-pages branch via GitHub Pages.

Lecture Format#

Always structure each individual lecture with the Audience & Learning Objectives in mind (see relevant chapter), compatibly with the idea that the students may be exposed to the presented topic for the first time.

For this reason, make sure that:

  • The jergon is suitable for the Audience, who are experts in the field of Astrophysics, but not in that of statistical analysis or machine learning; therefore, do not give for granted any formula (provide derivation and explanation), expand the acronyms you introduce, etc.

  • The code implementation is as simple as possible, without fancy solutions unless specifically requested by the user; if in doubt, opt for the simplest code solution.

Notebook Conventions#

Every notebook must follow Template_Notebook/Template_Notebook.ipynb exactly. This ensures consistent style and correct rendering on Jupyter Book (the primary target). Diverging from the <div> block patterns below will break rendering.

Required structure#

The following blocks are mandatory to be present for each lecture:

  • Credits block — must be the first cell (fieldset with logo table and <br> after)

  • Title — # Title <a class="tocSkip"> so it does not appear in the ToC

  • Setup section — commented-out #!pip install ... cell, then the Colab clone snippet, then the plot style loader (fetched via requests from the assets-public repo)

  • End marker — last code cell must be ###EOF

The remaining blocks are at the discretion of the user.

Global Style#

  • Template is the ground truth: If any of the rules in this chapter contradict the Template Notebook, use the standard in the Template Notebook.

  • Language: English

  • Code style: Students are demanding but not necessarily expert in Python. When creating the notebooks, never opt for fancy solutions like:

    • using fancy plots,

    • use fancy display of data and dataframe,

    • use extra widgets and libraries that can embellish the layout of the products. Keep an up-to-date requirements.txt with exact versions of the packages that are required.

    • DataFrame naming: All pandas DataFrame variables must be named with a df_ prefix (e.g. df_fx, df_data, df_clean). Using df alone is acceptable only for the single main working dataframe. Never use suffixed forms like clean_df, or bare names like fx, result.

    • Logic code must be simple and explicit: No lambda functions, no chained one-liners, no clever idioms. Break operations into multiple lines with named intermediate variables. A plain for loop or if/else block is always preferable to a compact expression.

    • Document main code blocks: Functions must have a docstring. Non-trivial code blocks (transformation steps, joins, validation logic) must have inline comments explaining what the code does and why.

  • Titles:

    • Do not use numbering in titles/sub-titles: the markdown hashing is enough.

  • Text: When asked to create or edit text, respect the following rules.

    • The text in the markdown blocks must be complete and descriptive.

    • Use short sentences.

    • Do not stack more than 2 sentences without a spacing.

    • When markdown prose mentions a count or number of repetitions, write it as a numeral, regardless of standard style conventions. Example: write “This notebook shows 2 ways”, not “This notebook shows two ways”.

    • Use formulas as deem fit.

    • Boldface 1 term per sentence when you want to stress some concept.

    • Boldface terms corresponding to definitions, at first appearance.

    • Never combine ** with `: Do not bold an inline-code term. Use either bold (for prose terms) or backticks (for code/identifiers), never both on the same token — e.g. write `GET` or GET, never GET.

    • No unexplained acronyms: Always spell out the full term at first appearance, with the short form in brackets, e.g. “Active Galcatic Nucleii (AGNs)”. Use the short form thereafter. This applies to every acronym, including Astrophysics ones — never assume one is known.

    • Simple lexicon; introduce every term: Prefer plain, everyday words over jargon. Do not take any technical or astrophysical concept for granted: when a domain term first appears, define it in one short, plain sentence. Write so a non-specialist can follow, even though examples stay grounded in Astrophysics, Statistics and Machine Learning. When a plain word works as well as a specialist one, use the plain word.

    • Never reference other lectures explicitly: Do not write “previous lecture”, “next lecture”, “earlier/later lecture”, or similar. Each notebook must read as self-contained. If a concept from elsewhere is needed, restate it briefly in neutral terms (e.g. “as is common when cleaning data”) without pointing to another lecture.

  • Formulas:

    • Do not use “\mathbf”, but “\boldsymbol”.

    • You do not need double “" inside formulas, e.g. this works: \(\lambda\), this not: \(\\lambda\)

    • Surround formulas using “\(" (inline) or "\)$” (centered), not “(“.

    • For italics variables, use “$”, not “(“.

    • Lower-case “x” and “y” are for univariate variables, upper-case “X” and “Y” are for multivariate variables.

    • Use “\hat{.}” for best-fitting parameters, and estimates (e.g, \hat{\theta} or \hat{y}).

    • If not already introduced, explain each variable in a formula, with a text starting with “where” right after the formula. If less than 3, explain in a sentence, otherwise as a bullet point list.

  • Equations: Use $\tag$ to number equations, so you can recall them in text; e.g. Equation <nn>.

  • Figures:

    • When inserting a figure always add a caption, and update the sequential caption numbering (e.g., Figure 1., Figure 2., etc.) across the notebook if necessary.

    • Caption format: use <figure> / <figcaption> HTML tags as shown in Template_Notebook.ipynb. Do not use italics on the caption text itself; <i> is only for references. Use <code> for inline code in captions.

    • Consider 2 types of figures: plots and illustrations.

    • Plots: Plots are part of the lecture flow, and are generated in-notebook; their code is integral part of the notebook.

    • Illustrations: Illustrations are diagrams, infographics, flows, diagrams, concept schematics, visual summaries of frameworks, etc.; this can be uploaded by the user in the images/ folder, or generated.

      • When you are asked to generate an illustration, create it programmatically using Python (matplotlib, PIL, or SVG markup) unless specifically required otherwise.

      • Do not place the code to generate illustrations inside the notebook, but place it in separate files “fig_*.py” inside the subfolder /images, then display the images as imports.

      • Do not number illustration files: e.g., fig_2_example.png shall just be fig_example.png.

      • Fonts must be readable: do not generate huge illustrations with tiny text.

      • Default accent palette: "steelblue" (1st), "firebrick" (2nd), "mediumseagreen" (3rd); beyond that fall back to matplotlib’s default cycle ("C3", "C4", …).

      • Where an illustration you cannot generate is needed, use an empty placeholder, and just write the caption and a reference to it, so that the user may obtain it.

Exercises#

  • Do not number Exercises, do not use markdowns (#, ##, ###, etc.): they will break Jupyter Book.

  • Each exercise title must include a time estimate in brackets, e.g. **Exercise — Title [20 min]**.

  • Use a tags to wrap the title, e.g. Exercise [45 min]

  • The font size shall be relevant to the section the exercise refer to: an exercise shall be a sub-section of the section it refers to. In this sense:

    • corresponds to a markdown chapter (“#”)

    • corresponds to a markdown sub-chapter (“##”)

    • corresponds to a markdown sub-sub-chapter (“###”)

  • Overestimate time — students see the topic for the first time

  • Exercises are applications, not extensions. If asked to create an exercise, only demand students to use Python features, functions, and patterns that have already been introduced earlier in the same notebook. Never introduce new syntax, new library methods, or new concepts inside an exercise.

  • Always provide a solution when asked to generate an exercise.

  • Solution stays in the same notebook (not a separate file)

  • Wrap solution between <div class="alert alert-danger" ...>[Solution below]</div> and [End of solution] divs

Sections#

  • Use # and ## headings only; for deeper nesting use bold, underline, or caps in plain text

  • Alternate short text blocks (1–2 sentences) with code, color blocks, or figures — avoid long prose
